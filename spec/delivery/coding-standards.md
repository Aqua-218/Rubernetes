# 10. コーディング規約

> 対象読者: すべての実装者、レビュア
>
> 状態: 規範、版0.2

Ruby、FFI、エラー、並行性、不変性、メタプログラミング、形式仕様との対応についての規約を定義する。

<a id="sec-10-1"></a>
## 10.1 方針

各規則には根拠を付ける。根拠を書けない規則は採用しない。「一般に良いとされているから」は、根拠として認めない。

規則の厳しさは、層によって変える。低い層ほど、誤りの影響が広く及び、発見も遅れるためである。

| 層 | 厳しさ |
|---|---|
| FFI、ランタイム、ネットワークのうち、システムコールを直接呼ぶ部分 | 最大 |
| Raft、ストア | 高 |
| コントローラ、スケジューラ、agent | 標準 |
| CLI、テストの補助 | 緩い |

<a id="sec-10-2"></a>
## 10.2 分類

各規則には、強さと確認方法を付ける。

| 強さ | 意味 |
|---|---|
| M | 必須。逸脱を認めない |
| R | 要求。逸脱するときは記録を残す。記録の内容は[10.9](coding-standards.md#sec-10-9)に定める |
| A | 推奨。逸脱は自由 |

| 確認方法 | 意味 |
|---|---|
| 機械 | 機械的に判定できる。CIで強制する |
| レビュー | 機械的に判定できない。レビューで確認する |

<a id="sec-10-3"></a>
## 10.3 R-1 FFIとシステムコール

### R-1.1（M、機械）

すべてのシステムコールの戻り値を検査する。

根拠: 失敗を見逃すと、kernel側の状態が想定とずれたまま処理が進む。問題が現れる場所と、原因のある場所が大きく離れる。

### R-1.2（M、機械）

`errno`は、システムコールの直後に読む。

根拠: あとに続くライブラリの呼び出しが、`errno`を上書きする。

### R-1.3（M、レビュー）

確保した資源は、同じ所有権オブジェクトと耐久性のある台帳で管理する。対象は、fd、マウント、namespace、cgroup、VMである。取得する前の意図、取得したあとのidentity、解放の状態を対にして記録する。異常終了のあとも、[5.8.4](../node/runtime.md#sec-5-8-4)の逆順で回収できるようにする。

根拠: リークしたマウントやnamespaceは、プロセスが終了しても残る。ホストを汚し、次回以降の起動を妨げる。

### R-1.4（M、レビュー）

定数には出典を注記する。対象は、システムコール番号、フラグ、netlinkの型である。

根拠: 値が正しいかどうかを、コードからは判断できない。検証するには、ヘッダと突き合わせる必要がある。

### R-1.5（R、レビュー）

構造体のレイアウトは、アーキテクチャごとに定義する。サイズはテストで検証する。

根拠: パディングとアラインメントの誤りは、一見動くが、特定の条件でだけ不具合を起こす。

### R-1.6（M、レビュー）

順序に意味のある操作には、その順序にする理由をコメントに書く。

根拠: `no_new_privs`とseccompのように、順序を入れ替えるとエラーも出ずに無効になる組み合わせがある。

<a id="sec-10-4"></a>
## 10.4 R-2 エラー

### R-2.1（M、機械）

例外を握りつぶさない。`rescue`の本体を空にしない。

根拠: 分散システムでは、握りつぶしたエラーが、別の場所に遅れて不整合として現れる。原因の特定が難しくなる。

### R-2.2（M、機械）

`rescue`には、捕捉する例外クラスを明示する。`rescue => e`と`rescue Exception`を禁止する。

根拠: 制御用の例外や割り込みまで捕捉してしまう。

### R-2.3（R、レビュー）

同期的な再試行には、回数の上限と待ち方を明示する。収束のために必要な非同期の再試行には、最大のバックオフ、キャンセルの条件、耐久性のあるキューを明示する。

根拠: 制御されていない再試行は、障害のときに負荷を増やす。一方、要求を恒久的に捨てると、desired stateへの収束が成り立たなくなる。

### R-2.4（R、レビュー）

回復できない状態では、すみやかにプロセスを終了する。不整合な状態のまま処理を続けない。

根拠: 破損した状態で処理を続けると、被害が回復できない範囲まで広がる。

<a id="sec-10-5"></a>
## 10.5 R-3 並行

### R-3.1（M、レビュー）

共有する可変の状態は、必ず同期の仕組みを通して参照する。

根拠: コントローラはreconcileを並行して実行する。同期していない読み書きは容易に起きる。

### R-3.2（R、レビュー）

ロックを取得する順序を文書に書き、その順序に従う。

根拠: デッドロックの実質的な原因は、取得順序の不一致だけである。

### R-3.3（R、機械）

Threadを生成する場所を集約する。任意の場所で生成しない。

根拠: 生成する場所が分散すると、停止処理に漏れがないことを確認できない。

### R-3.4（M、レビュー）

同じPodに対する操作は直列化する。

根拠: 起動と削除が並行すると、解放済みの資源を操作してしまう。

<a id="sec-10-6"></a>
## 10.6 R-4 不変性

### R-4.1（M、レビュー）

内部表現のリソースオブジェクトは、不変として扱う。更新するときは複製してから行う。

根拠: 共有キャッシュの上のオブジェクトを変更すると、無関係なコントローラの判断が変わる。

### R-4.2（M、機械）

キャッシュから返すオブジェクトはfreezeする。

根拠: R-4.1を、規約ではなく仕組みで保証するためである。

### R-4.3（R、レビュー）

破壊的なメソッドは、自分のスコープで生成したオブジェクトにだけ使う。`!`の付くメソッドや`<<`などが当たる。

根拠: R-4.1と同じである。

<a id="sec-10-7"></a>
## 10.7 R-5 動的機能

### R-5.1（M、機械）

`eval`と`instance_eval`に文字列の引数を渡さない。

根拠: 静的解析ができなくなり、規約を機械的に判定できなくなる。

### R-5.2（M、機械）

標準ライブラリと外部gemのクラスを再定義しない。

根拠: 影響がプロセス全体に及ぶ。局所的な検証では捉えられない。

### R-5.3（R、レビュー）

`define_method`による定義は、スキーマコンパイラが生成するものに限る。対象は、型、コーデック、Manifest DSL、コントローラとスケジューラの登録である。使う場合は、生成されるメソッド名を一覧にできなければならない。

根拠: APIの型は宣言的に書くのが適切であり、それはRubyの利点でもある。一方、無制限に使うと、呼び出せるメソッドの全体を把握できなくなる。

### R-5.4（R、機械）

`send`でprivateメソッドを呼ばない。

根拠: カプセル化の境界が意味を持たなくなる。

### R-5.5（M、機械）

スキーマ、GVK、フィールド、プラグインの解決に、`method_missing`と`respond_to_missing?`を使わない。

根拠: 名前の打ち間違いを実行時まで検出できない。生成したAPIの全体を、RBSと静的検査に公開することもできなくなる。

**R-5.6 M 👁** user supplied Ruby DSL は cluster credential を持たない隔離 process で評価し、
明示的な信頼承認なしに実行しない。
根拠: Ruby DSL は設定データではなく任意コードであり、manifest の閲覧とコード実行を同一視できない。

<a id="sec-10-8"></a>
## 10.8 R-6 形式仕様との対応

**R-6.1 M 👁** TLA+ 仕様に対応する実装箇所には、
対応する動作名をコメントで示す。
根拠: 仕様と実装の対応が失われると、
検証結果が実装について何も保証しなくなる。

**R-6.2 M 👁** Lean で証明した性質に依存する実装箇所には、
定理名をコメントで示す。
根拠: 同上。加えて、実装変更時に
どの証明を再確認すべきかを判断できるようにする。

**R-6.3 R 👁** 仕様を変更した場合、
対応する実装とコメントを同一の変更単位で更新する。
根拠: 分離すると乖離が生じる。

<a id="sec-10-9"></a>
## 10.9 R-7 文書

**R-7.1 M 👁** コメントには「なぜ」を書く。「何を」は書かない。
根拠: 「何を」はコードから読める。重複した記述は
コード変更時に更新されず、誤った情報として残る。

**R-7.2 M 👁** 規約から逸脱する場合、逸脱記録を残す。
記録には、逸脱した規則番号、理由、影響範囲、
代替の安全確保手段を含める。
根拠: 逸脱そのものは避けられない。
避けるべきは、理由が失われた逸脱である。

**R-7.3 M ⚙** 規範仕様、schema、release artifact に未決マーカー、期限のない作業注記、
「実装時に決定」を残さない。
根拠: 未決のまま実装すると複数 component が異なる仮定を採用し、互換性を判定できなくなる。

<a id="sec-10-10"></a>
## 10.10 適用しない規則と理由

以下は検討した上で採用しない。

| 規則案 | 不採用の理由 |
|---|---|
| 1 メソッドの行数上限 | Ruby ではブロックにより行数が自然に伸びる。行数と理解容易性の相関が弱い |
| 循環的複雑度の上限 | 根拠が経験則に留まり、本プロジェクト固有の理由を示せない |
| 再帰の禁止 | 木構造（所有グラフ、OverlayFS 層）の処理で再帰が自然。深さは入力により有界 |
| 例外の全面禁止（Result 型） | 標準ライブラリが例外を投げるため境界で変換が必要になり、変換漏れという新たな誤りを生む |
| `nil` の禁止 | Kubernetes API は未設定と空を区別する。`nil` の排除は表現力を失う |
